## 개인 프로젝트 — 네이버 SEO 분석 솔루션 (진행 중)

`Next.js 16 / React 19 / TypeScript / Node.js / Prisma / PostgreSQL / Redis / BullMQ / NextAuth.js / Puppeteer / Recharts`

- 한 줄: 업체의 시드 키워드로 네이버 검색 생태계에서 '이길 수 있는 기회 키워드'를 찾고, 키워드별 콘텐츠 처방전(채널·구조·AI 브리핑 최적화)을 생성하는 B2B SEO 분석 도구. 기획·설계·개발 단독 진행.

**[2개 데이터 레이어 설계 — 수요(API) + 랭킹(크롤링)]** 
검색량/경쟁도 같은 수요 데이터는 검색 결과 화면에 노출되지 않아 네이버 검색광고 API로만 얻을 수 있고, SERP 배치·상위 콘텐츠 구조 같은 랭킹 데이터는 API로 얻을 수 없어 크롤링이 필요했습니다. 이를 '수요 레이어(API)'와 '랭킹 레이어(크롤링)'로 분리하고, 수요로 후보를 좁힌 뒤 소수만 깊게 크롤링하는 파이프라인을 설계했습니다.

**[네이버 API 게이트웨이 — HMAC 인증 추상화]** 
검색광고 API, DataLab, 검색 API를 연동하며, 공통 인증·헤더 로직을 abstract base client에 두고 각 API 클라이언트가 상속하는 구조로 설계했습니다. 일일 호출 제한(검색광고 10만/일 등)에 대응해 Redis 캐싱(TTL)으로 호출량을 통제했습니다.

**[기회 점수화 — 노이즈를 지우지 않고 가라앉히는 설계]** 
연관 키워드 최대 500개에 대해 `수요 × (1-경쟁도) × 관련성`의 가중합으로 기회 점수를 산출하고, 접미사 패턴 기반 검색 의도(정보형/상업형/거래형/탐색형)를 분류해 우선순위 키워드를 선별합니다. 무관한 키워드도 삭제하지 않고 점수로 하단 정렬하여, 다른 시드에서 재활용 가능한 데이터 손실을 방지했습니다.

**[SERP 크롤링 — 비용 통제 + 방어 로직 (설계)]** 
기회 필터를 통과한 20~50개만 Puppeteer로 크롤링하여, 영역별 노출 구조와 상위 콘텐츠 구조(글 길이·키워드 밀도·소제목·이미지·콘텐츠 형태)를 분석합니다. 요청 간격·robots.txt 준수, 수집 실패/이상치 감지 후 마킹, 셀렉터 헬스체크, AI 브리핑 DOM 불안정 대비 fallback 셀렉터 체인 등 방어 로직을 설계에 포함했습니다.

**[AI 브리핑 화이트스페이스 공략 (설계)]** 
네이버 AI 브리핑(2026년 신규 영역)의 인용 소스·구조 패턴을 분석해, 처방전에 'AI 브리핑 인용을 노리는 콘텐츠 구조(FAQ/비교표)'를 반영하도록 설계했습니다. 전문 분석 도구가 아직 없는 신규 영역을 선점 포인트로 삼았습니다.

**[레이어드 아키텍처]** 
Route Handler → Service → Repository → Infrastructure로 책임을 분리하고, feature별 도메인 모듈화(keyword/serp/audit/rank), zod 기반 설정·요청 검증, 외부 의존성 인터페이스 추상화(테스트 시 mock 교체), 커스텀 에러 체계를 적용했습니다. 크롤링은 BullMQ 워커로 비동기 처리합니다.

배포에는 Blue/Green 전략으로 무중단 전환하였으며 완료 후 이전 포트의 프로세스를 종료하며, 실패 시 이전 릴리스 디렉토리가 보존되어 즉시 롤백이 가능합니다.

그 결과,  배포 시 사용자에게 서비스 중단 없이 새 버전이 반영되어 운영 안정성과 사용자 경험을 향상시켰습니다.

**[Nuxt 3 SSR/CSR 하이브리드 렌더링 전략]**
SEO와 초기 로딩 속도를 위해 SSR/CSR 하이브리드 전략을 설계했습니다. 개발 및 유지보수 시 Hydration Mismatch 빈도를 줄이기 위해 미들웨어 파이프라인(IP 접근 제어, 인증, 메뉴 관리, 렌더 권한, 레이아웃 선택)을 분리하여 생산성을 상승시켰습니다.

Static JSON와 Spring Cache로 2단계 캐싱 구조를 적용하여 로딩 속도를 개선하여 Lighthouse 점수 93점을 달성하였으며, 백엔드 서버 장애가 있더라도 안정적인 페이지 로딩으로 가용성을 확보하였습니다.

**[동적 게시판 테마 렌더링]**
수십개의 게시판 유형을 동적으로 렌더링하는 구조를 설계했습니다. 게시판 유형별 테마 컴포넌트(리스트, 검색박스, 페이지네이션)를 조합하여 list, view, write 모드를 동적 렌더링합니다.

이 구조를 통해 신규 게시판 테마 추가 시 테마 디렉토리에 컴포넌트만 추가하면 되고, 라우터나 빌드 설정 변경이 불필요합니다. 백엔드 동적 게시판 CRUD 서비스와 결합하여 코드 변경 없이 관리자 UI에서 새 게시판 유형을 정의하면 즉시 운영할 수 있는 동적 게시판 시스템을 구현했습니다.

**[JWT+Redis 하이브리드 인증]**
강제 로그아웃, 권한 변경 즉시 반영, 슬라이딩 세션 방식 요구사항을 충족시키기 위해 유효한 세션만 Redis에 저장하는 화이트리스트 방식을 채택했습니다. Health Check를 통해 Redis 장애 시에는 Graceful Degradation으로 전환하였습니다.

이를 통해 운영 요구사항을 충족하면서도 Redis 장애 시에도 서비스 가용성을 유지하는 인증 체계를 구축했습니다. 세션 만료 시각을 프론트엔드에 전달하여 클라이언트 측 자동 로그아웃 타이머와 서버 인증 상태 간의 동기화를 확보했습니다.

**[JDBC Template 기반 동적 게시판]**
모든 게시판 유형의 데이터가 하나의 테이블에 집중되는것을 막기 위해 게시판 유형별로 독립 테이블을 런타임에 생성하는 동적 게시판 구조를 설계했습니다. JDBC Template 기반 동적 SQL 빌더를 선택했습니다.

테이블 분리를 통해 게시판별 데이터 규모가 관리 가능한 수준으로 유지되어 단일 테이블 LIKE기반 검색과 복합 검색조건 시 병목 해소되었고, 각 테이블에 최적화된 인덱스를 독립적으로 적용할 수 있게 되었습니다.

이 엔진을 통해 신규 게시판 유형 추가 시 코드 변경 없이 관리자 UI에서 필드를 정의하면 즉시 사용 가능한 게시판이 생성됩니다. 프론트엔드 테마 렌더링 엔진과 결합하여 완전한 동적 게시판 시스템을 구현했으며, Elasticsearch 색인과 연계하여 분산된 동적 테이블의 데이터를 통합 검색할 수 있는 구조를 확보했습니다.

**[Redis Streams를 활용한 로그인 AOP에서 CRUD 전체 감사 로깅]**
로그인 성공 및 실패 이력을 포함한 콘텐츠 생성, 수정, 삭제, 권한 변경, 회원 관리 등 모든 CRUD 작업의 감사 추적이 필요했으나, 기존 로깅 유틸리티는 애플리케이션 로그(SLF4J)에만 기록하여 DB 검색이 불가능했습니다. CRUD 감사 이벤트는 수백 명의 사용자로도 빈도수가 높아 DB에 직접 쓰기 부하를 줄이기 위해 비동기 Redis Streams로 구현하였습니다.

또한 k6 기반 부하 테스트(최대 300 VU, 평균 80~120 RPS) 환경에서 Redis Streams 감사 이벤트 성능을 검증하였습니다. 처리량은 초당 약 1,000건 수준에서도 Consumer backlog가 평균 0~5 범위로 안정적으로 유지되었으며, 감사 로깅 활성화 전후 API p95 응답 시간 증가 폭을 5ms 이하로 제한하여 핵심 트랜잭션 성능에 미치는 영향을 최소화하였습니다.

**[상속 권한 조회 최적화 및 Redis 노드별 캐싱]**
기존 레거시 구조를 개선하기 위해 pathId(dot path) 필드를 도입하여 메뉴의 전체 경로를 문자열(예: "1.3.8")로 기록하여 조상 조회는 문자열 분할 한 번으로, 하위 노드 조회는 LIKE 접두사 쿼리 한 번으로 처리하였습니다. 

Redis 캐싱은 전체 권한을 하나의 키에 담지 않고, 메뉴 노드별로 분리하였습니다. 

그 결과, 재귀 쿼리 제거와 단일 쿼리 조상 조회로 권한 조회 쿼리 수가 75% 감소하고, Redis 노드별 캐싱으로 응답 속도가 20ms 이하로 10배 이상 개선되었습니다. 

**[Elasticsearch 통합 검색 시스템 구축]** 
동적 게시판 구조로 테이블이 분산되면서 통합 검색을 Elasticsearch와 Nori를 도입하여 분산 테이블의 데이터를 단일 인덱스에 통합 색인하고, 한국어 기반 풀텍스트 검색을 구현했습니다. 

색인 시 공개 상태, 사이트 식별, 메뉴 권한까지 다차원으로 색인하여 텍스트 매칭과 권한 필터링을 단일 쿼리로 처리하며, Transactional Outbox 패턴으로 DB 트랜잭션과 색인 동기화의 일관성을 보장했습니다. 재색인 시에는 Read/Write Alias Swap 전략으로 검색 서비스 중단 없이 인덱스를 전환합니다.

이를 통해 k6 기반 검색 부하 테스트(30~50 RPS) 환경에서 약 80만 건 규모 인덱스를 기준으로 권한 필터 포함 통합 검색의 평균 응답 40ms, p95 85ms 수준을 유지하였으며, 검색 오류율은 1% 미만으로 안정적으로 동작함을 확인했습니다.

**[폐쇄망-외부망 보안 데이터 연동 및 ETL 프로세스 구축]**
클라이언트의 조직, 회계 등 내부 핵심 데이터가 폐쇄망에 격리되어 있어 외부망 서비스에서 활용할 수 없는 구조적 제약이 있었습니다. 폐쇄망 API와 인증서 기반 암복호화 통신으로 데이터를 수신하고, 이기종 시스템 간 스키마 차이를 정제/변환하는 ETL 프로세스를 구축하여 외부망 DB로 연동하는 파이프라인을 설계했습니다.

이를 통해 수동 데이터 이관 작업을 자동화하고, 조직/회계 데이터의 정합성을 유지하면서 외부망 서비스에서 실시간에 가까운 데이터 활용이 가능한 구조를 확보했습니다.

**[LLM 기반 설계/개발 프로세스 도입]**
사내 클라이언트 접수 관리 시스템 개발에 AI 기반 개발 방식이 요구되었으나, CLI 환경에서 LLM을 실질적인 설계/개발 워크플로에 적용한 경험자가 없어 주도적으로 프로세스 도입을 진행했습니다. Claude Code CLI와 BMad 에이전트 프레임워크를 활용하여, MD 산출물 기반의 표준화된 설계 프로세스를 구축했습니다. 또한 LLM이 생성한 설계 및 코드 초안을 서브 에이전트로 재검증하는 단계를 추가하여 품질을 확보했습니다.

이를 통해 설계 문서 작성 및 초기 개발 시간을 대폭 단축하였으며, 설계 의사결정의 일관성을 확보하여 신규 기능 확장 및 도메인별 고도화 작업의 효율성을 향상시켰습니다.

**[Trouble Shooting: Gradle에서 Task와 Process 충돌 빌드 실패 이슈 해결]**
QueryDSL Q클래스 생성 Task와 MapStruct 어노테이션 Process가 동일 라운드에서 실행되며 빌드 실패가 반복되는 문제가 발생했습니다. Lombok, MapStruct, QueryDSL 세 프로세서가 같은 컴파일 단계에서 경합하면서 Q클래스를 참조하지 못하거나 매핑 코드 생성이 실패하는 것이 원인이었습니다.

QueryDSL Q클래스 생성을 -proc:only 옵션으로 별도 JavaCompile Task로 분리하고, compileJava가 이를 의존하도록 실행 순서를 명시했습니다. MapStruct와 Lombok은 메인 컴파일 단계에서만 동작하도록 조건 분기하여 프로세서 간 간섭을 제거했습니다. 또한 디버깅용 classpath 출력 Task를 추가하여 빌드 문제 발생 시 원인 추적이 가능한 구조를 확보했습니다.

이를 통해 빌드 안정성을 확보하고 CI/CD 파이프라인에서의 빌드 실패를 제거했습니다.

**[Trouble Shooting: 메뉴 동기화 탐색 병목 현상 해결]**
커스텀한 @ExecutionTime으로 메뉴 트리구조 동기화 메서드가 500ms를 초과하는 병목을 발견하였습니다. 이를 해결하기 위해 pathId 컬럼을 도입하고, DFS에서 BFS로 전환하여 같은 깊이의 노드를 일괄 처리하도록 개선하였습니다.

- 동기화 시 같은 깊이의 노드를 한 번에 배치 저장하고 pathId를 CONCAT 쿼리로 일괄 갱신
- DB 호출 횟수가 노드 수 비례에서 트리 깊이 비례로 감소

이를 통해 500ms에서 150ms으로 약 70% 개선하였으며 경로 탐색 로직이 간소화되어 코드 가독성을 높였습니다.

**[Trouble Shooting: 게시판 도메인 무결성과 통일성 확보]**
런타임 동적 게시판 생성 서비스를 구현하며 게시판 관리 테이블, 필드 관리 테이블, 실제 게시판 데이터 테이블의 무결성과 통일성을 확보하였습니다.
- JVM Lock 처리: 단일 애플리케이션 운영 환경에 맞춰 JVM Lock으로 동시 생성 요청 간 경합을 방지하였습니다.
- 보상 롤백 처리: JDBC 기반으로 DDL을 제어하므로 트랜잭션 롤백이 불가하여, 예외 시 메타/정의 테이블과 물리 테이블을 단계별로 복구하는 보상 롤백을 구현하였습니다.
- 소유자 검증: 보상 롤백 시 DROP 대상이 해당 요청에서 생성된 테이블인지 소유자 검증을 수행하여, 기존 테이블의 오삭제를 방지하였습니다.

**[Evidence-based: 적극적인 문서화를 통한 상호 커뮤니케이션 강화]**
다양한 비즈니스 요구조건에 맞는 파이프라인 구현, 프론트 미들웨어, 백엔드 인증 등 철저한 문서화를 통해 업무 효율성과 팀 간 커뮤니케이션을 강화했습니다. 구두 설명으로 인한 비효율을 줄이고, 팀의 생산성을 높일 수 있도록 체계적으로 기록하였습니다.
